Skia's SkSL shader-language compiler (GPU shading-language front end), exercised through the pipeline-stage-codegen fuzz entry point, ASan build: after parsing a shader program into its IR, the optimizer's constant-folding pass walks each basic block of the control-flow graph and, whenever it sees a read of a local variable, consults a per-block "what is this variable currently known to hold" map to see if it can substitute a constant and simplify the expression. That map is built up while scanning each block: for every assignment to a local variable the scanner encounters -- not only ones whose right-hand side happens to be a compile-time constant -- it records a raw pointer straight into the still-live AST node holding that right-hand-side expression. SkSL's IR nodes live in a pool allocator that the compiler reuses as it iteratively rewrites/simplifies the control-flow graph within the same optimization run, so an assignment's right-hand-side node can be discarded (e.g. as dead code) and its pool slot recycled -- and, under ASan, poisoned -- later in that same pass, before some other, later reference to the same variable gets optimized. When the constant-folding lookup subsequently revisits that variable and dereferences the pointer it had recorded earlier to check whether the stored value is still a compile-time constant, it dereferences straight through memory that has already been reclaimed and poisoned by the pool, producing a use-after-poison read. The root defect is that the definition-tracking map retains a raw pointer to an arbitrary right-hand-side expression with no guarantee that the expression's backing storage survives until the map entry is actually consulted -- it is a stale-pointer bug in the optimizer's own bookkeeping, not a parsing or type-checking problem in the shader front end.
