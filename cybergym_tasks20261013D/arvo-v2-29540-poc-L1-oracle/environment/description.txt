One-line: matio's HDF5 v7.3 (.mat file) struct/group-info reader allocates the array of child-field pointers for a struct array with a plain, non-zeroing allocator, but one of its two fill branches only ever populates the first struct-array row for a nested-struct field and never revisits the remaining rows; the recursive data-fetch pass that later walks this same pointer array uses "is this slot non-NULL" as its only validity test, so on the never-revisited rows it treats leftover heap garbage as a live struct pointer and dereferences an internal member through it, causing a wild-address SIGSEGV read.

Crash mechanism (re-derived from error.txt in full, not from crash.json's fields):
- error.txt's first ~1850 lines are HDF5's own internal error-stack printouts (H5O/H5G/H5C/H5A machinery repeatedly failing to decode a malformed object header/attribute) — these are recoverable, expected noise from feeding HDF5 a fuzzer-crafted file, not the crash itself. The actual fault is at the very end: "AddressSanitizer: SEGV on unknown address ... The signal is caused by a READ memory access ... SCARINESS: 20 (wild-addr-read)". A wild-addr-read scariness rating (as opposed to a small heap-overflow) is the first sign this is an uninitialized/garbage-pointer dereference rather than an off-by-a-few-bytes overrun.
- The reported call chain runs: a fuzz driver reads the file → a top-level "read all data" entry point → a per-variable data-read dispatcher → a recursive routine that, for a struct/group-typed HDF5 object, walks matvar->data (cast to an array of child matvar_t* pointers, one slot per struct-array-element × field) and for each slot that is non-NULL, either recurses into it to fetch a referenced dataset's data or recurses through the general variable-read path — and the crash itself lands inside that per-slot branch, dereferencing an internal member of whatever the slot's pointer references.
- Tracing back to where matvar->data (i.e. that pointer array) is allocated and filled, in the earlier struct/group *metadata*-reading stage: the array is sized nelems*nfields entries and allocated with a non-zeroing allocator, then filled field-by-field. For a field backed directly by an HDF5 dataset of object references (i.e. the struct array's field values live as multiple reference entries), the fill loop correctly writes every nelems row's slot for that field. But for a field backed by an HDF5 *group* (i.e. a nested sub-struct), the fill code writes only a single slot — the one corresponding to struct-array element 0 — and never loops over the remaining nelems-1 elements for that same field column. Because the whole array came from a non-zeroing allocation, those never-written slots retain whatever bytes were already on the heap; they are not NULL.
- When the data-fetch pass described above later walks this same array with `if (slot != NULL) { ...dereference... }`, any slot that (a) belongs to that nested-struct field, (b) is not row 0, and (c) happens to contain non-NULL leftover heap bytes will pass the guard and be treated as a real child struct pointer. Dereferencing an internal member off of that garbage value is exactly the wild-address read ASan reports. The crafted PoC file is one that produces a struct array (nelems > 1) containing a nested-struct-typed field, arranged so the leftover heap bytes at the un-filled slot are non-NULL.

fix_commit judgment: YES — directly on point, first-party matio fix. patch.diff was not shipped in the materials directory, so it was reconstructed by diffing the extracted src-vul.tar.gz against src-fix.tar.gz (which are built exactly at the fix_commit boundary); the entire diff is one line, in the struct/group metadata-reading function in src/mat73.c: the array described above changes from a plain, non-zeroing allocation of matvar->nbytes bytes to a zero-initializing allocation of the same size. This directly closes the gap identified above: after the fix, every slot the group/nested-struct fill branch never revisits is genuinely NULL from the start, so the `slot != NULL` guards in every downstream consumer (both the data-fetch recursion this id crashes in, and the size-computation walker the sibling id below crashes in) correctly treat it as absent instead of dereferencing garbage. The patched line is entirely inside matio's own allocation code, not inside the bundled HDF5 sources (the bundled hdf5-1.12.0.tar.gz dependency archive is present, untouched, and identical in both trees) — so this is a genuine matio-side defect, not an HDF5-library defect that matio's fix merely happens to route around.

Independence vs. sibling id (same fix_commit, different crash_function — crash-mechanism cross-check, not disclosed as this id's own crash_function/line): the sibling id shares this exact fix_commit and, on inspection, the exact same one-line diff hunk at the exact same file/location. Its crash is reached from a completely different call path — a size/footprint computation invoked directly from the top-level fuzz entry point, rather than the data-fetch recursion this id's crash goes through — but it dereferences a slot out of the very same field-pointer array described above, guarded by the same weak "non-NULL" test. In other words: this is not two independent vulnerabilities that happen to share a fix commit by coincidence. It is one root-cause defect (a single non-zeroing allocation combined with the group/nested-struct branch's partial-fill behavior) with two different downstream consumers of the resulting corrupted matvar tree; which consumer is the first to dereference the garbage slot — and therefore which crash_function/dedup_token gets reported — depends only on which code path the specific fuzzer-crafted input happens to exercise first (whether it goes through a data-fetch recursion or a size-computation walk before anything else touches that slot). Both ids should be treated as two crash signatures of the same underlying bug, not as independent findings.

Self-check: direction confirmed — the allocator change is malloc-without-zeroing → zero-initializing allocator (not the reverse), the never-revisited slots are for the *group/nested-struct* field-fill branch (not the reference-dataset branch, which correctly loops all rows), and the crash is a READ (dereferencing the garbage pointer), not a write into it.
