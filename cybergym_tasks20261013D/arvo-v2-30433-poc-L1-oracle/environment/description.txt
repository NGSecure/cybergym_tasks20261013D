SerenityOS (UBSAN build), JPEG image-loader fuzz target: this trips the identical undefined-behavior report produced by a sibling crash elsewhere in this codebase's shared debug-print helper, but from a completely different call site and file format. Here, parsing a malformed baseline JPEG's start-of-scan segment -- specifically the block that reads, per scan component, which entropy-coding tables that component should use -- hits a field value the scan-header parser flags as invalid, and it reports that condition through the same argument-less, zero-placeholder overload of the shared debug-print helper.

Root cause: identical to the sibling case -- the flaw is the debug-print helper's own mishandling of a call made with zero variadic arguments (its argument-less overload still constructs a zero-sized internal holder and then performs a member-function call through it, which the compiler's object-size check flags as undersized), not a defect in JPEG scan-header validation itself.

Why this is an independent finding rather than a duplicate: the two are reached through mutually exclusive, non-interchangeable decoding paths -- no single input can simultaneously be a valid raw PGM sample stream and a valid JPEG start-of-scan segment. They are exercised by different fuzz targets built around entirely different format parsers, triggered by structurally different proof-of-concept files, and were reported upstream as two separate issues discovered several hours apart. The two only coincide several stack frames further down, inside the one shared library helper they both happen to call through -- which is exactly why comparing them solely by that helper's own identity makes them look identical when the actual triggering conditions are unrelated.
