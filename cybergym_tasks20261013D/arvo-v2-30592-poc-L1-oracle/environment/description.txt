In wolfMQTT (ASan, MQTT v5 build), the client keeps one generic "current incoming message" object that it reuses, uncleared, across separate wait-for-packet calls: any packet that doesn't match what a given call is specifically waiting for (or a plain "wait for anything" call) gets decoded into this same shared object every time, so whatever a previous decode left inside it is still present when the next unrelated packet is decoded into it. When a later incoming packet is a DISCONNECT carrying MQTT v5 properties, the properties parser (MqttDecode_Props, in src/mqtt_packet.c) walks that shared object/receive-buffer state without it having been reset since the earlier decode, and its byte-by-byte length/type walk runs into memory tied to an earlier network read that has already completed and been released elsewhere - a heap-use-after-free READ.
