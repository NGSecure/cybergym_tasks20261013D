SerenityOS (UBSAN build), BMP image-loader fuzz target: decoding a malformed Windows BMP file that selects the run-length-encoded pixel-data path causes the loader's RLE-decompression step -- while unpacking an encoded scanline -- to encounter a run/escape byte sequence it flags as invalid, and it reports that condition through the same argument-less string overload of the shared debug-print helper implicated in three other catalogued image/interpreter findings in this codebase (a PGM sample-stream reader, a JPEG scan-header parser, and a BMP DIB-header/color-table decoder), plus a second BMP-loader finding in this same batch.

Root cause: the same shared-library defect as those siblings -- the debug-print helper's zero-argument overload builds an internal, zero-sized holder for the call's (nonexistent) type-erased arguments and then performs a member-function call through it, which the compiler's object-size check flags as operating on storage too small for a valid object of that type.

This finding shares its fuzz target and file format with the previously catalogued BMP DIB-header/color-table finding and with a second finding in this same batch, but is reached through a third, disjoint decode phase: RLE-compressed pixel-data decompression, entered only once header parsing and color-table setup have already succeeded, and exercised by its own malformed-BMP PoC distinct from either sibling's. It shares no code path with the PGM or JPEG findings at all.
