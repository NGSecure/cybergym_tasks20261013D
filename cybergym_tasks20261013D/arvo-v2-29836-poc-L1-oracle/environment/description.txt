一句话：matio 在读取 MAT v7.3（即 HDF5 容器）文件里某个 cell 数组变量的元素引用列表时，按文件自身声明的元素个数 malloc 出一块*不清零*的缓冲区去接收 HDF5 的读取结果，既不检查该次读取是否真的成功/完整写满了这块缓冲区，也不逐个校验每个槽位是否被真正填入了有效的引用值，就把这整块内存原样交给 HDF5 去逐个解引用；一旦某些槽位实际上没有被写入（例如文件里声明的元素数与该引用数据集实际能读出的内容不一致），残留的堆分配垃圾字节会被当成合法的“对象引用令牌”继续往下传，最终在 HDF5 内部尝试从这些字节里解出一个编码长度/数值时，被 MemorySanitizer 判定为读取了未初始化内存。

崩溃机制（对照 error.txt 全文重新推导，而非照抄 crash.json 字段）：
- MSan 报的是 use-of-uninitialized-value，触发点在 HDF5 内部一个用来从对象头 / 引用令牌里解码出一段变长编码地址长度的函数里；它的直接调用链是：把某种 native VOL 层的“令牌”转换成文件内地址 → 依据该地址打开对象（native VOL object-open）→ 上一层通用的 VOL object-open 分发 → `H5Rdereference2`（旧式引用解引用 API）。
- 再往上追，`H5Rdereference2` 是被 matio 的 `Mat_H5ReadDatasetInfo`（mat73.c:718）调用的，而这次调用本身又是从 `Mat_H5ReadNextReferenceInfo`（mat73.c:1002）触发的，`Mat_H5ReadNextReferenceInfo` 又是被另一处 `Mat_H5ReadDatasetInfo`（mat73.c:720）调用——也就是说，matio 在读取某个 cell/字段引用指向的对象时，会递归地去读该被引用对象自身的数据集信息，本次崩溃发生在这条递归链的某一层解引用上。
- error.txt 里给出的三段 DEDUP_TOKEN“未初始化值来源”回溯链把根因钉得很死：
  1) 最外层：未初始化值在 HDF5 的“native 令牌转地址”转换函数内部被存入内存（即上面提到的转换步骤本身），说明这块内存在被写入时就已经不完整；
  2) 中间层：真正把这些字节从 matio 提供的缓冲区搬进 HDF5 内部“令牌”结构的操作，是 HDF5 引用解码逻辑里的一次 memcpy（在处理旧式对象引用格式时按原始字节整段拷贝，不区分哪些字节真正有效）；
  3) 最底层（堆分配溯源）：这块内存最初就是在 matio 的 `Mat_H5ReadDatasetInfo` 里通过 `malloc(nelems*sizeof(*ref_ids))` 分配出来的（对应 vul 源码里处理“该变量是 cell 数组”分支的那处引用缓冲区分配语句），分配后紧接着调用一次 HDF5 的批量读取把整块 cell 数组的元素引用一次性读进这块缓冲区，但对这次读取的返回值未作任何检查，随后不加区分地对缓冲区里的每一个槽位（从 0 到 nelems-1）逐个发起解引用。
- 三段回溯拼起来就是完整因果链：matio 相信“文件声明有 nelems 个 cell 元素，就应该能读出 nelems 个有效引用”，却既不清零这块内存、也不检查读取是否真的把每个槽位都写满，就把它整体当作已经全部有效的引用数组去逐个解引用；一旦其中有槽位实际未被写入合法数据（因为该 cell 数组对应的引用数据集本身内容不完整或与声明的元素个数对不上），HDF5 在沿着这个“看似合法”的引用向下打开对象、试图从其令牌里解出地址长度时，读到的就是这块堆内存里残留的分配时垃圾字节，从而被 MSan 抓获。

fix_commit 判断（`0ce6d1e329a8949383ea5f28b32f096acc2f60d9`，理由具体）：
- 直接比对 vul/fix 两份 `src/mat73.c`：fix 版本恰好把上面第 3 点提到的、位于 `Mat_H5ReadDatasetInfo` 处理 cell 数组分支里的那处 `malloc(nelems*sizeof(*ref_ids))` 改成了 `calloc(nelems, sizeof(*ref_ids))`，并把原本无条件执行的“读取+循环解引用+释放”整体包进了一个“分配是否成功”的判断里。该改动所在的源码行号与 error.txt 第三段 DEDUP_TOKEN 回溯里记录的堆分配调用点行号精确对应，不是巧合命中。
- 这个改动直接掐断了本次崩溃的必要条件：`calloc` 保证缓冲区在读取前先被清零，即便后续读取因为某些槽位对应的引用数据实际缺失/不完整而没能覆盖全部字节，遗留下来的也是确定性的 0，而不是分配时残留的、内容不可预测的堆垃圾——HDF5 后续对这些槽位做“解引用→解码地址”时不会再读到未初始化内存。虽然 fix 依旧没有去检查那次批量读取本身的返回值（也就是说“该读的元素个数是否真的读到”这一校验缺口本身并未被补上），但这个缺口本来就不是本次 MSan 未初始化值告警的成因（告警成因是“缓冲区内容不可预测”，而不是“分配失败”或“函数调用失败被忽略”），所以不影响这里 fix_commit 与崩溃点直接相关的判断。
- 与本 session 此前在 matio 项目上遇到的 29517（crash_function 位于 HDF5 内部、但当时的 fix_commit 经核实与崩溃点完全不搭边、真正修复在 HDF5 上游仓库）不是同一种情况：这里的缺陷源头明确在 matio 自身——是 matio 分配了一块未清零、且未经完整性校验的缓冲区并直接交给 HDF5 处理，HDF5 内部那个做地址解码的函数只是“最终读到垃圾字节的地方”，并非它自身逻辑有边界检查缺陷；matio 把分配方式从 malloc 改成 calloc，是能够从根上消除“垃圾字节被当作合法引用值使用”这一条件的正经修复，因此判定 fix_commit 与本崩溃直接相关、机制自洽。
