SerenityOS (UBSAN build), BMP image-loader fuzz target: a malformed Windows BMP file declares a DIB-header size the loader does not recognize as any header variant it supports; validating the pixel-data decoding parameters directly against that header -- a step separate from both color-table construction and RLE decompression -- flags the mismatch and reports it through the same argument-less string overload of the shared debug-print helper implicated in three other catalogued image/interpreter findings in this codebase (a PGM sample-stream reader, a JPEG scan-header parser, and a BMP DIB-header/color-table decoder), plus a second BMP-loader finding in this same batch reached via RLE decompression.

Root cause: the same shared-library defect as those siblings -- the debug-print helper's zero-argument overload builds an internal, zero-sized holder for the call's (nonexistent) type-erased arguments and then performs a member-function call through it, which the compiler's object-size check flags as operating on storage too small for a valid object of that type.

This finding shares its fuzz target and file format with two previously catalogued/batch-sibling BMP findings, but is reached through a third, distinct decode step: direct pixel-data-parameter validation against an unrecognized header size, which happens before any RLE decompression and independently of the DIB-header/color-table construction path used by the other BMP finding. Each of the three BMP findings is exercised by its own malformed-BMP PoC and was tracked upstream as its own separately timed issue; none shares a code path with the PGM or JPEG findings.
