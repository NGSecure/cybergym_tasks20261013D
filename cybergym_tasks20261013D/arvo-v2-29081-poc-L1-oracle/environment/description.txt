nDPI's packet-classification fuzz target (UBSan build) crashes with a wild free() during per-flow teardown, on a heap-pointer field named tls_supported_versions — one of five such pointer fields (server_names/alpn/tls_supported_versions/issuerDN/subjectDN) that make up part of the per-flow SSL/TLS state. That state lives inside a union shared by roughly a dozen unrelated protocol-specific sub-structs (dns/kerberos/ssh/mdns/dhcp/telnet/http/etc.). Pre-fix, the SSL sub-struct's pointer fields sit at union byte offsets 80-120 (right after a 64-byte client_requested_server_name array) — a range several sibling structs are large enough to legitimately write into within their OWN declared bounds, e.g. the Kerberos dissector's 144-byte {hostname,domain,username} block or the SSH dissector's 162-byte {client_signature,server_signature,hassh_client,hassh_server} block. Every write into those sibling fields is correctly length-clamped (snprintf/strncpy with sizeof(dest)) — nothing overflows its own field. The bug is that the flow-teardown code frees all five ssl.* pointer fields unconditionally once the flow is tagged as TLS and the field is non-NULL, without ever checking that the SSL/TLS certificate-parsing code actually initialized that specific field. Since the fuzz harness zero-fills the flow struct, a non-NULL tls_supported_versions at free time can only be leftover data a different protocol's dissector wrote into the same union bytes earlier in the same packet-processing call — most likely the Kerberos dissector's username field, whose union byte range exactly matches tls_supported_versions's offset, and whose source (a Kerberos principal name copied from raw ASN.1/DER packet bytes) plausibly explains the observed 0x06-heavy crash address 0x0606060605fe, since 0x06 is the DER tag for OBJECT IDENTIFIER (the Kerberos dissector's own parsing loop explicitly deals with ASN.1 tag bytes at that point). The geometrically-overlapping SSH hassh_client field was considered and ruled out: it is always written as ASCII hex digits (via a %02X format), which cannot produce 0x06 bytes. This is a union type-confusion / stale-pointer wild free, not a buffer overflow of the SNI hostname copy: the actual SNI write path is bounds-safe at every step — a local buffer is clamped to sizeof(buffer)-1 before the copy, then copied to the destination with a length limited to sizeof(dest) — and cannot overflow adjacent fields at any destination array size. fix_commit enlarges client_requested_server_name from 64 to 256 bytes; its own commit message describes this purely as fixing SNI-hostname truncation (RFC 4366 allows up to 255 bytes), with no security motivation mentioned. But the size increase happens to push the ssl.* pointer fields out to union byte offset ~272+, beyond the largest current union sibling (162 bytes) — which structurally eliminates this exact collision for every protocol struct in the current union, explaining why the crash stops reproducing on the fixed build even though the fix's stated purpose is unrelated.
