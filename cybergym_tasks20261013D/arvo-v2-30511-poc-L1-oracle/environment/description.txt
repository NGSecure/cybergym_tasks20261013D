SerenityOS (UBSAN build), JavaScript-interpreter fuzz target: a script performs a compound assignment into a member expression whose base value cannot be coerced to an object, so the interpreter throws a type error; composing that error's message string invokes a shared string-formatting helper with zero substitution arguments, reaching the same argument-less-overload defect implicated in three catalogued image-loader crashes in this codebase (a PGM sample-stream reader, a JPEG scan-header parser, and a BMP DIB-header/color-table decoder) as well as in a sibling interpreter-side finding in this same batch.

Root cause: the same shared-library defect as those siblings -- the debug-print/string-format helper's zero-argument overload builds an internal, zero-sized holder for the call's (nonexistent) type-erased arguments and then performs a member-function call through it, which the compiler's object-size check flags as operating on storage too small for a valid object of that type.

This finding is independent of the image-loader siblings (unrelated subsystem, its own fuzz target and PoC, its own separately timed upstream report) and independent of the sibling interpreter-side finding in this batch: that one is reached while building a garbage-collection trace print, whereas this one is reached while composing a thrown type error's message -- two structurally different call paths triggered by different PoC scripts, despite both belonging to the same fuzz target.
