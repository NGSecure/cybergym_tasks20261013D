FlatBuffers' JSON-parsing fuzz target (ASan build) round-trips a JSON document into a Monster flatbuffer and then re-serializes the result back into JSON text; a heap-buffer-overflow read occurs while printing a byte-vector field that carries the schema's nested-flatbuffer attribute, because the text-generation code unconditionally dereferences the field's raw vector bytes as an embedded flatbuffer's root-offset header without first checking that the vector actually holds enough bytes for that header — when the vector is empty, its data pointer sits right at the end of a live heap allocation, and the 4-byte header read runs off the end of it. What lets an otherwise-invalid document reach that print path at all: the parser's tokenizer used to fuse a leading '+'/'-' sign together with a following bare word into one opaque token, and tagged that fused token with the very same token kind used for quoted string literals, purely so numeric fields could accept sign-prefixed named constants (things like +inf/-nan). Because the fused token carried a string-literal token kind, the type-matching code for an unrelated, string-typed field could not distinguish a bogus, unquoted, sign-prefixed word from a genuine quoted string, and silently accepted it as that field's value — letting a document that should have failed to parse succeed instead. The same document also supplies an explicit empty array for the nested-flatbuffer-tagged field, so once parsing wrongly succeeds, serialization walks straight into the unguarded header read above. The fix pulls the sign-handling logic out of the general-purpose tokenizer entirely: the tokenizer now hands back only the bare sign character by itself, and the sign+following-word recombination is moved into the one call site that legitimately needs it, which first requires the following token to genuinely be a bare identifier before splicing the sign back onto it. A sign-prefixed bogus word can therefore no longer be mistaken for a valid value of some other field type, so the malformed document is rejected during parsing itself, before it can ever reach the still-unguarded nested-flatbuffer print path.
