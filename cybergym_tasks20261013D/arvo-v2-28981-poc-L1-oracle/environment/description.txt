YARA's .NET module fuzz target (ASan build) crashes with a heap-buffer-overflow read of 2 bytes while decoding metadata table rows from an embedded PE assembly's compressed "#~" stream. One table's row layout includes a column that indexes into the "#Blob" heap; the parser resolves this to a blob (offset, length) pair and then reads a fixed 2-byte value from the start of that blob before consulting the blob's own encoded length. The sanity check applied beforehand only confirms that offset+length stays inside the overall mapped assembly buffer — it does not confirm the blob is actually big enough to contain the 2-byte value the code is about to read from it. Root cause: the code is missing a minimum-length requirement on the resolved blob entry, so a row referencing a very short (near-empty) blob located right at the end of the mapped input still passes the existing bounds check, and the immediately following fixed-size read then runs past the true end of the allocated buffer.
