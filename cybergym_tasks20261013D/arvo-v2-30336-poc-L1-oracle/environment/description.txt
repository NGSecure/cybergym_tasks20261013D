cryptofuzz's RELIC module runs a bignum base-conversion self-check after ECDSA-Verify: it serializes a RELIC bignum to an ASCII string via one of RELIC's own string-writing routines and reads that string straight back in, and MemorySanitizer flags a use-of-uninitialized-value the moment the harness calls `strlen()` on the buffer that routine was supposed to have fully filled. The root cause is entirely inside RELIC's own arithmetic: the string-writer's digit-extraction loop repeatedly calls one of RELIC's small internal single-digit division helpers to peel off one output digit per iteration, and that helper allocates its internal quotient temporary with the library's fixed, generic default precision instead of sizing it to the actual dividend's digit count -- unlike a near-identical sibling helper elsewhere in the same file, which already sizes its own temporary correctly. When the bignum being converted needs more digits than that fixed default provides for, the division routine's low-level digit-fill step writes past the end of the undersized temporary's backing storage, and the corrupted quotient then flows back into the working copy the enclosing loop uses on its next iteration -- causing the loop to register the value as zero one iteration early. That leaves the tail of the caller's output string buffer never written, still holding leftover allocator bytes, and the following `strlen()` call is the first place anything reads that uninitialized memory.
