Tesseract's libFuzzer API fuzz target (ASan build): a heap-use-after-free read occurs inside the legacy OCR post-processing pass that resolves I/l/1 character-shape ambiguities in a recognized word. That routine fetches two views of the word's current best-choice text — the decoded UTF-8 string, and right after it the per-character byte-length table — through two back-to-back accessor calls on the recognition result, keeping only a raw C-string pointer into the first view's underlying buffer. Root cause: both accessors are just two different windows onto the same pair of long-lived, mutable scratch buffers cached on the best-choice object, and each accessor call unconditionally rebuilds *both* buffers from scratch as a side effect — not just the one the caller asked for — before handing back a reference into them. So the second accessor call, made to fetch the length table, silently discards and reallocates the very buffer that the first accessor's pointer is still referencing; the routine's next step then scans that now-stale pointer's characters looking for the ambiguous glyphs, reading through already-freed heap memory instead of the live string.
