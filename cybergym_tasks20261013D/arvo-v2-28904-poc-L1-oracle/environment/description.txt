In Skia's SkSL shader compiler (ASan build), reached from SkRuntimeEffect::Make() when it parses and constant-folds an attacker-supplied runtime-effect shader source, a vector `==`/`!=` comparison first confirms that its two top-level operand expressions share the same C++ expression subclass before dispatching into a virtual constant-comparison routine, but when that routine is a prefix (unary negation) expression it recurses one level deeper into each side's inner operand without re-checking that the two inner operands are still the same subclass. A shader whose comparison operands fold asymmetrically under negation - one side collapsing all the way down to a resolved vector-literal constructor node, the other still wrapped in one extra, not-yet-cancelled negation layer around what would otherwise be the same underlying node - drives that recursive call into a routine that expects its argument to be a constructor node (with a small dynamic array of component sub-expressions) and unconditionally treats it as such, without first checking the argument's real runtime kind. Since the argument is actually the differently-shaped, differently-sized negation-wrapper node, the routine ends up reading the constructor node's "component array" field at a memory offset that, in the real object, was never part of it - spilling past the true object's extent into the not-yet-handed-out region of SkSL's per-compile bump-pool arena. AddressSanitizer's pool-region poisoning (the arena poisons memory it hasn't allocated out yet) flags the resulting 8-byte pointer read as a use-after-poison.
