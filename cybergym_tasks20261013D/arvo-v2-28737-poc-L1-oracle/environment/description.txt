kimageformats (ASan build): parsing a malformed GIMP XCF image drives the XCF layer-loading routine into a state where the very first layer used to build up the output image is set up from corrupted data, and a later layer crashes when it is composited on top of that already-broken image.

Each layer record in an XCF file carries two byte offsets, read straight out of the file, that tell the parser where to jump to find that layer's pixel-tile hierarchy and (optionally) its mask. The parser seeks the input stream to each offset in turn but never checks whether the seek actually landed on a valid position -- the run log shows a long series of warnings that the requested seek target is wildly out of range (huge positive values, and even negative ones), meaning these offsets are essentially garbage relative to the real size of the input. When a seek like that is rejected, the stream is simply left sitting wherever it happened to be, and the code goes on to read tile/hierarchy data from that unintended position exactly as if the jump had succeeded.

For the first visible layer in the file, that layer's (corrupted) width/height and pixel-tile data are used to build the single shared output image that every subsequent layer gets painted onto. Because its hierarchy offset failed to seek to a real location, the tile data backing that shared image ends up built from whatever bytes were actually at the stream's current position rather than the layer's real pixel data, leaving the image object's internal state inconsistent with what its declared dimensions imply.

The crash itself does not happen on that first layer -- it happens once a second layer is parsed and the code tries to merge it into the already-initialized shared image using Qt's normal drawing API. Constructing a painter object bound to that image requires Qt to read through the image's internal device-private bookkeeping, and by this point that bookkeeping is not merely absent (which Qt handles gracefully) but populated with a plausible-looking, attacker-influenced large value left over from the earlier corruption -- so the very first step of setting up the painter, before any actual drawing happens, dereferences that bogus value as if it were a real internal pointer and the process receives a segmentation fault on a wild, high-value address.

In short: two attacker-controlled stream offsets used for per-layer seeks are never validated for success, so a failed seek silently desynchronizes the parser instead of aborting, letting the routine that assembles the first layer's contribution to the output image consume unrelated file bytes as if they were valid pixel/tile data; the resulting corruption doesn't surface until a later layer is merged in and Qt's painting machinery is handed a paint device whose internal state is no longer well-formed.

fix_commit note: the commit pinned as the fix for this crash makes no change to any parser or application source file at all -- its only content is a single line added to a project housekeeping/ignore-list file (a build-artifact directory being excluded from version control), and it introduces nothing resembling a seek-result check, a bounds check, or any other validation anywhere in the layer/hierarchy-loading path described above. This is not a plausible fix for a memory-safety crash in the image parser. This id is very likely another instance of the same bisection-artifact pattern already seen elsewhere in this project (day-granularity build-boundary bisection landing on an unrelated repository-maintenance commit rather than the actual patch), and the pinned fix_commit should not be trusted as a description of what closes this crash.
