wolfSSL's OpenSSL-compatibility layer allocates a WOLFSSL_HMAC_CTX (which embeds the library's internal Hmac state, including a field that records which hash algorithm is in use) with a plain heap allocation and does not zero the memory. Nothing forces a caller to run the normal HMAC-init path before touching that context; the OpenSSL-style API also exposes a deep-copy operation that duplicates one HMAC context's internal state into a freshly allocated one. That copy routine decides which per-algorithm state-copy helper to invoke by branching on the source context's recorded hash-algorithm field. When the copy is performed on a context that was only just allocated and never run through the init path, that field still holds whatever bytes happened to be on the heap at allocation time rather than a value the algorithm ever wrote — so the branch reads and dispatches on uninitialized memory, which is what a memory-sanitized build flags. The specific reproducer here follows exactly this shape: create a fresh HMAC context, then immediately copy it (via the OpenSSL-compatible duplicate-context call) without ever initializing it with a key/algorithm first, and the copy path faults while switching on the (uninitialized) algorithm field.

Fix-commit judgment: the diff recorded against the listed fix commit only edits a comment in an unrelated bignum-math header (fixing mojibake in an author-name credit) — it does not touch the OpenSSL-compat HMAC code at all and cannot plausibly be what stopped this crash. Diffing the vulnerable and fixed source snapshots directly shows the actual behavioral change lives in the HMAC-context allocation function itself: the fixed version zero-initializes the newly allocated context right after the heap allocation, before returning it, so the embedded hash-algorithm field starts at the library's defined "no algorithm selected" value instead of raw heap garbage. With that field at a real, defined value, the deep-copy routine's dispatch on an un-initialized context now deterministically falls through to its "unrecognized algorithm" failure path instead of branching on undefined memory contents — eliminating the uninitialized read. So the recorded fix commit appears to be a mismatch (most likely a day-granularity OSS-Fuzz bisection artifact landing on an unrelated same-day commit), not the true fixing change; the true fix is the zero-initialization added at context-allocation time.
