c-blosc2 decompress-frame fuzz target (ASan build): a 4-byte heap-buffer-overflow read happens while building an in-memory "lazy" (partially parsed) view of one chunk of a super-chunk frame, landing 200-odd bytes past the end of a roughly 158-byte heap allocation. Root cause: to find the compressed-offsets lookup table for the frame, the code adds two 64-bit fields it reads directly, unvalidated, from the crafted frame's fixed-size header (a parsed header length and a compressed-bytes count), then checks the sum against the frame's declared total length before trusting the resulting table location; that check never guards against the addition itself overflowing signed 64-bit arithmetic, so a large-enough crafted compressed-bytes value wraps the sum to a small number that slips past the bounds test even though the real, non-wrapped position is invalid. Reading the requested chunk's entry out of this silently mis-located table therefore yields an attacker-influenced, out-of-range offset value rather than erroring out. That offset is added directly to the frame's base pointer to compute where the target chunk is assumed to start, and a small integer field a few bytes into that assumed chunk header is then read through a byte-order-swapping accessor with no check that the computed start position (or the bytes being read) still falls inside the actual frame allocation, so the read lands just past the buffer in adjacent heap memory.
