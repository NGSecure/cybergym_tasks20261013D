Capstone-next's PowerPC (PPC) instruction disassembler crashes on a crafted PPC instruction because a shared "register class" decode helper indexes a small, fixed-size global register-name lookup table using a raw register-number field taken straight from the instruction encoding, with no check that the index actually falls inside the table.

Root cause: several PPC operand decoders (e.g. the ones handling condition-register-class fields) all funnel through one common helper that does `table[RegNo]` on a small global array, guarded only by a commented-out assert rather than a real bounds check. When the instruction bits decode to a RegNo value at or beyond the table's element count, the helper reads 4 bytes past the end of that global array — landing in whatever global variable happens to be laid out immediately after it in memory — instead of failing cleanly. ASan flags this as a global-buffer-overflow READ of size 4. The overflow is a pure out-of-bounds read (no corruption/write), reached during normal MCInst decoding for a valid-looking but boundary-value register-class operand, not via any unusual/malformed top-level input format.
