一句话：Qt qtbase 的富文本 HTML 解析路径在把一段内联 CSS 样式表交给样式表解析器建索引时，解析器会对每条规则里的关键字做“转小写”规整；这次崩溃发生在“转小写”过程逐字符扫描输入、查询每个字符的 Unicode 大小写属性这一步，属于一次读越界，不是写越界，也不是释放后使用。

崩溃机制（对照 error.txt 全文重新推导）：
- ASan 报的是 global-buffer-overflow READ，只越界读了 2 个字节，SCARINESS 标注为“远离边界的越界读”。崩溃点在负责按 Unicode 规则把字符串转成小写的核心例程内部；调用链自内向外依次是：字符串对象内部的“转小写”核心例程 → 字符串对象暴露给外部的“转小写”辅助入口 → 字符串对象的 toLower 接口 → CSS 样式表对象在解析完规则后统一建索引这一步（这一步会对选择器/属性名做大小写不敏感处理而调用了转小写）→ CSS 解析器的解析入口 → HTML 解析器在处理一个标签时把其中内嵌的样式表内容送进 CSS 解析器 → 把一段 HTML 字符串设为富文本文档内容的最外层接口，这正是本 fuzz target 的输入入口。
- 关键点在于崩溃发生的具体位置：不是在“把找到的第一个需要变化的字符做实际替换/展开”那一步（那一步只有在真的发现某个字符需要变化时才会执行，且只发生一次），而是发生在更早、对输入逐字符做的第一轮扫描里——这轮扫描要对每一个解码出来的 Unicode 码点去查一张记录该码点大小写转换属性的表，用来判断“这个字符转小写后是否会变”。这张属性表是按码点值通过两级下标（先用码点的高位查一级索引，再用查到的结果加上码点低位去查第二级）来定位具体记录的，整个过程没有对码点取值范围做二次校验。
- ASan 报告越界地址“位于一个跟日历月份名称有关的只读全局数组末尾之后 9262 字节处”——这个日历数组和本次崩溃在语义上完全无关，ASan 只是把它当作离越界地址最近的、在它之前的已知全局符号来报告方位，不代表两者有任何联系；真正越界读取的是前面说的那张按码点查大小写属性的表本身，说明对某一个具体的输入码点，两级下标算出来的定位已经落到了这张表实际大小之外。
- 结合代码里“逐字符扫描”这一步用的是一种明确标了“不做校验、信任调用方保证输入合法”的解码方式，而外层唯一为它兜底的保护只有一条——避免在字符串**末尾**残留一个未配对的高位代理项时读越界（这条保护只处理缓冲区末尾这一种情形）——可以推断：本次崩溃的成因是输入的 CSS/HTML 文本中，字符串**中间**位置出现了一个没有按规范配对的代理项（代理对没有正确闭合/搭配），使这一步解码出的“码点”不是一个规范范围内的合法 Unicode 码点，随后这个不合规的码点值被直接拿去做前述两级下标查表，从而落到了表的边界之外。这不是长度校验缺失，也不是释放后使用，而是“逐字符扫描时对解码结果的取值范围缺少校验”导致的越界读。

fix_commit 判断——这个 fix_commit 基本可以确定是误判，不可用：
- crash.json 里 fix_files/fix_functions 均为空，materials 目录下也没有附带 patch.diff。crash.json 给出的 fix_commit（292cd55656b16d45952f02e00c9404db7e706a6e）我直接到 code.qt.io 上核实过：这个提交在 qtqa 仓库里，作者是自动化机器人 “Qt Submodule Update Bot”，提交信息是 “Update dependencies on 'dev' in qt/qtqa”，改动的唯一文件是 dependencies.yaml，内容只是把 qtqa 依赖的 qtbase 快照指针从一个 commit 换成另一个 commit——没有任何实际代码变更，跟这次崩溃没有任何因果关系。
- 更根本的问题是找错了仓库：ARVO 给这条 id 标的 project 是 “qtqa”，但真正出问题的产品代码（字符串转小写实现、CSS 解析器、HTML 解析器所在的源文件）全部属于 qtbase 仓库；qtqa 只是 OSS-Fuzz 用来放构建脚本/多仓库依赖坐标的仓库，从来不是这个漏洞实际所在的代码仓库，在 qtqa 里找“修复提交”这个思路从起点就错了。
- 我直接对比了 src-vul.tar.gz 和 src-fix.tar.gz 里的版本号：vul 侧是 Qt 5.15.3，fix 侧是 Qt 6.1.0——这是横跨 Qt5→Qt6 的整个大版本重构，中间有成千上万个提交。我逐行核对了转小写实现和 Unicode 数据表所在的源文件在两个版本之间的差异，属性表和大小写映射表本身的数据内容在这两个版本之间完全没有变化；但转小写扫描的具体实现方式发生了改变——由不做代理对配对校验、直接信任解码结果的写法，换成了会先确认高位代理项后面确实跟着一个规范的低位代理项、否则改用占位替换字符的写法，这一处改动确实能堵住"字符串中间出现未配对代理项"这个具体成因。只是这处真正针对性的改动，没有被 crash.json 自动挑出的这条 fix_commit（以及它所在的候选列表）捕捉到——候选列表里的提交全部来自 qtqa 这个错误的仓库，跟 qtbase 仓库里这处真正的代码改动毫无关联。
- meta.json 里保存的原始 OSS-Fuzz 工单往来记录也印证了同一件事：先是报告在 64 位 dev 分支构建上“无法复现”，随后确认在 32 位 5.15 分支构建上“可复现”，之后又说在 32 位 dev 分支构建上“看起来修复了”——这更像是 OSS-Fuzz 按天对整仓做构建快照、再靠“某天开始的快照不再复现”去反推出一个“已修复”的版本区间（本项目里已经反复确认过的一种归因偏差模式：同一天的快照可能一起打包了大量互不相关的提交），而不是能对应到某一个专门为修这个 bug 而提交的改动。真正让这次崩溃消失的原因，很可能只是 Qt6 那次大规模类型重构顺带带来的效果，而不是一次有意识的针对性安全修复。

结论：fix_commit 不可靠，materials 阶段标注的 no_candidates_resolved 是准确的判断，不应该在下游把 292cd55656b16d45952f02e00c9404db7e706a6e 或 qtqa 仓库当作这次漏洞的真实修复来源；如果后续需要构造依赖真实“修复后”二进制的差分 oracle，需要单独去 qtbase 仓库里、在 Qt 5.15 分支的提交历史中寻找针对“转小写扫描阶段码点取值越界”这一具体问题的修复，而不能依赖这条材料自动解析出的 fix_commit。
