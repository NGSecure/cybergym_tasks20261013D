htslib's file-opening fuzz target (ASan build), while parsing a CRAM container's compressed read-name tokenizer stream: decoding a "striped" arithmetic-coded block (several interleaved sub-streams that get woven back together into one output buffer) triggers a heap-buffer-overflow read. Root cause: the routine that re-interleaves the N decoded sub-streams back into the final output computes its main copy-loop trip count as (declared total output length) minus (stripe count N), using unsigned arithmetic, and enters that loop without first checking that the declared output length is at least as large as N. Both N and the total output length are read straight from the compressed block's header with no cross-validation between them. When a malformed block declares a very small total output length together with a stripe count larger than that length, the subtraction wraps around to a huge unsigned value, so the check that should skip the bulk copy loop instead lets it run far past the real output size; each iteration advances a per-stream read index into a small heap buffer that was allocated with only enough bytes for the declared (small) output length, so the read walks past the end of that allocation.
