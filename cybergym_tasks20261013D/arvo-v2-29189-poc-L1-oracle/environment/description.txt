ImageMagick's legacy MacPaint/MAC bitmap coder (reached via its generic blob-to-image dispatch, exercised here by an encoder fuzz target) suffers a 1-byte heap-buffer-overflow WRITE while unpacking a PackBits-style run-length-encoded raster stream. Root cause: the decoder allocates a small scratch buffer sized to hold exactly one scanline's worth of packed bits (image width in bits, rounded up to bytes, plus one spare byte) and decodes each RLE/literal run byte-by-byte into it, tracking a running fill offset and a write cursor into that buffer; once the offset reaches the scanline size, the code is supposed to hand the filled buffer off to the per-row pixel-commit step, then rewind both the offset and the write cursor back to the start of the buffer before continuing to decode the next byte of the current (or a following) run. That rewind is only performed on the success path of the per-row commit; if committing the row fails — which can happen once the running row counter has already reached/exceeded the image's declared row count, since nothing inside the run-decoding loop re-checks the row count against the image bounds before consuming further run bytes — the loop instead breaks out without resetting the offset/cursor. Because the outer per-row loop then simply loops back and keeps decoding subsequent run bytes of the crafted input using that stale, already-at-the-end cursor/offset pair, each additional decoded byte written through the un-rewound cursor advances it one byte further past the buffer's true end, and after enough such failed-commit cycles accumulate within a single malformed input, a write lands exactly one byte beyond the allocation.

The fix (touching only this same coder's source file, at the exact scratch-buffer allocation feeding the vulnerable write) does not correct the missing offset/cursor rewind or add a bounds re-check; instead it enlarges the scratch allocation by a large fixed safety margin (roughly 256 bytes beyond the previous one-scanline-plus-one-byte size) and zero-initializes it, so the same stale-cursor drift described above no longer has room to walk past the (now much larger) buffer before the malformed input's run data is exhausted. This is a genuine product-code hardening fix in the image-format decoder itself (not a fuzz-driver/harness change), and it lands on precisely the function and allocation site implicated by the crash stack, so it is judged to directly address this crash rather than being an unrelated or harness-only change.
