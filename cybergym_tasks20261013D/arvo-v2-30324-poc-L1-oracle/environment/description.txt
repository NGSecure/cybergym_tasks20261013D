A maliciously crafted DNG/TIFF raw-image file can drive LibRaw's floating-point-DNG raw decoder to write past the end of a heap-allocated pixel buffer while copying a row of raw sample data from the input stream, an AddressSanitizer-detected heap-buffer-overflow write.

Root cause: the floating-point-DNG raw decoder is only valid for pixel samples that are exactly 16, 24, or 32 bits wide, because it allocates its output buffer as an array of C `float` values (4 bytes per sample) up front, before it has read any actual per-tile row data. Which decoder handles a given file is decided earlier, while walking the file's TIFF/DNG tag directory: whenever the sample-format tag marks the data as floating point and the bits-per-sample tag is a multiple of 8 greater than 8, this floating-point decoder gets selected — but that selection check never puts an upper bound on the bits-per-sample value, so a crafted tag value larger than 32 (e.g. 40, 48, 56, 64) still selects it. Once inside the decoder, the number of bytes to read for one row of one tile is computed separately, straight from the file's declared bits-per-sample (rounded up to a whole byte count), with no cross-check against the 4-bytes-per-sample assumption baked into the earlier buffer-size calculation. When bits-per-sample exceeds 32, the per-row byte count computed at read time is larger than the per-row space the buffer allocation reserved for it, so the call that copies that row's bytes out of the input stream into the buffer writes past the buffer's end.
