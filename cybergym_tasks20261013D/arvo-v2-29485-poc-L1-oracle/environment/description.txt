One-sentence summary: Opening a crafted NTFS volume image and resolving an MFT entry that is referenced while assembling a fragmented attribute list triggers a 1-byte heap-buffer-overflow READ while validating and applying the update-sequence ("fix-up") marker embedded near the end of the freshly-read MFT record buffer.

Root-cause mechanism: Each MFT entry is read into a heap buffer sized to the volume's declared MFT-record size. Two on-disk 16-bit fields near the start of that buffer describe an "update sequence": a byte offset into the buffer where a small marker structure begins, and a count of how many 2-byte sector-tail slots the marker plus its trailing per-sector replacement array cover. Before the marker is ever dereferenced, the code is supposed to compute how many bytes the offset, the marker itself, and the per-sector array together would occupy, and reject anything whose total exceeds the buffer size. That computation folds the count into the formula as "(count - 1) sector-slots", so when the on-disk count field is exactly zero, the subtraction goes through signed promotion before being combined with the otherwise-unsigned byte totals; the negative term doesn't get caught as an invalid/oversized value, it instead silently cancels part of the addition and shrinks the effective bound by a couple of bytes compared to what a legitimate minimum count would require. A separate, earlier guard that could have caught a suspicious count value only runs when the count is nonzero, so a count of exactly zero skips it entirely and reaches the weakened check. The net result is that an MFT record whose declared update-sequence count is zero and whose offset field points just a byte or two before the true end of the record buffer is accepted as valid even though applying the marker at that offset would read past the allocation, and the very next statement dereferences the 2-byte marker value at that offset, reading one byte beyond the end of the heap buffer.

fix_commit assessment: fix_commit is confirmed correct for this crash — applying patch.diff to the vulnerable source tree and diffing the result against the official fix-commit source tree shows the touched file is byte-for-byte identical afterward, so there is no partial or multi-commit gap here (unlike the case seen elsewhere in this project where a single-commit diff missed part of a fix that spanned several commits). The patch adds an explicit up-front rejection of a zero update-sequence count (closing off the case that reaches the weakened arithmetic), adds an explicit upper-bound rejection of an implausibly large count, and rewrites the offset/size validation to use consistent unsigned arithmetic — computing the required trailing space by subtracting the per-sector array size from the buffer size rather than adding a term that can be negative before an unsigned promotion — so the same class of sign-related bypass can't recur for other count values either. This lines up exactly with the crash mechanism reproduced here.
