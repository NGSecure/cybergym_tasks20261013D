poppler 在把 PDF 里内嵌的 TrueType 字体写出为 PostScript 的非 CID（复合 Type 0/Type 42）字体程序时（qt_pdf_fuzzer 经由 PS 转换路径触发，对应字体的 CIDToGID 映射为隐式恒等映射、即未显式传入映射表的那条分支），读取了一个从未被赋值的栈上局部变量。

根因：负责读取该 TrueType 字体表目录的底层例程会逐条校验每个表项记录的偏移/长度是否落在文件范围内；如果字体被构造得使得每一条表项都被判定为越界/非法，有效表的数量会被清零，随之重新分配得到的表数组指针也变成了空指针。但表示"该字体对象已成功完成前期解读"的整体状态标志，在这一条特殊的清零分支里没有被相应地重置为失败，依旧停留在此前某个更早的检查点已经置真的旧值上。构造字体对象的公共入口（工厂函数）只依据这一个整体状态标志来判断是否把对象交给上层调用者使用，于是这个内部已经没有任何有效表、状态实际上残缺不全的对象，被当作一个正常解析成功的对象放行了出去。

随后，PS 输出层试图把这个（表面上合法、实际上空壳的）字体对象转换写出为 Type 0/Type 42 字体程序，需要用到由另一个内部子例程通过输出参数回传的"已使用到的最大字形编号"；但那个子例程一开始就要在表目录里查找一张必需存在的表，由于对象内部根本没有任何有效表可查，它会立即提前返回，全程都没有机会写入调用方传入的那个输出参数。调用方（外层的字体转换函数）随后在一处判断可输出字形数量的比较表达式里，直接读取了这个从未被写入过的局部变量，这就是 MemorySanitizer 捕获到的未初始化值使用。

fix_commit 的修改直接堵住了这个缺口：它在前述"有效表数量清零、表数组变空"的这条分支返回之前，补上了把整体状态标志显式重置为失败的一行代码。补丁生效后，构造字体对象的公共入口就能正确识别并拒绝这种内部残缺的对象（返回空指针给调用方），后续负责写出 Type 0/Type 42 字体程序的转换逻辑根本不会再作用到这类对象上，因而也就不会再走到那个提前返回、遗漏写出最大字形编号的路径——从根上切断了"未初始化局部变量被读取"的触发条件。这个改动与本次崩溃的根因是直接对应的：它修的不是别的旁支问题，正是"状态标志与对象实际完整性不一致"这一件事。
