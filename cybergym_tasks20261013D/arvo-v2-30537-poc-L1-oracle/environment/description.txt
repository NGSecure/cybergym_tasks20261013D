RELIC's big-number squaring, exercised by a bignum-arithmetic fuzz target (ASan build): squaring a sufficiently large multi-precision integer via its recursive Karatsuba routine triggers a heap-buffer-overflow write. Root cause: to split the operand into a high half and a low half, the routine allocates two scratch big-number temporaries using the library's generic "new" helper, which always reserves a fixed default precision (capacity) rather than sizing the allocation to how many digits the split actually needs; it then computes the half-width from the operand's own digit count and copies exactly that many digits into each scratch temporary's internal digit buffer without checking that width against the fixed capacity just reserved. When the input operand has enough digits that half its width exceeds the library's default precision, the copy into the (now too-small) buffer runs past the end of the heap allocation, producing a single-word out-of-bounds write.
