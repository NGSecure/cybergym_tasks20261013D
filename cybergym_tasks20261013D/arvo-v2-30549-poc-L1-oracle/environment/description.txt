This is a use-of-uninitialized-value bug (MemorySanitizer) triggered by GraphicsMagick's generic coder fuzz target when a MATLAB(MAT)-format image that was just decoded is immediately re-encoded back out to MATLAB format. The MAT v4 decode path allocates the destination image's pixel storage according to the width/height/type fields declared in the file's own header, but the routine that copies the file's raw sample bytes into that pixel storage does not guarantee it writes a value into every element the header promises: for a crafted input whose declared geometry doesn't line up with how much real sample data actually follows in the file, part of the freshly-allocated pixel buffer is left holding whatever was already on the heap, because the buffer itself is never pre-zeroed and the copy routine simply stops once it runs out of real bytes to consume rather than padding out the remainder. Right after decode, the same MAT v4 path applies an orientation-fixup step that rearranges the image by copying whole rows/columns from the buffer into a new arrangement; because this rearrangement is a blind element-by-element copy, it happily relocates the never-initialized elements right along with the legitimate ones, so the taint survives into the fully "decoded" image with no signal anywhere that some of its pixels were never really set. The crash itself does not happen during decode: it happens moments later when the fuzz target turns around and writes that same in-memory image back out through the MATLAB encoder, which — before it emits any pixel data — makes a first pass over every pixel of the image to decide whether the output can be collapsed to a single-channel (grayscale) matrix or must stay multi-channel. That decision pass reads each pixel's channel values unconditionally, with no way to know that some of the elements it is about to compare were never written by the decoder, so it ends up reading uninitialized heap memory during this pre-write classification scan rather than during any of the actual pixel I/O.
