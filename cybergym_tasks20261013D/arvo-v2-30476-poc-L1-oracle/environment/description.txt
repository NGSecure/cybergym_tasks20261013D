Skia's SkSL shader-language compiler (GPU shading-language front end), exercised through the runtime-effect fuzz entry point, ASan build: the crash surfaces inside the compiler's CFG-based optimizer, specifically in the pass that folds away assignments whose left-hand side turns out to be provably unused (dead-assignment elimination), while it is scanning an ordinary user-defined function containing a field assignment whose right-hand side is textually the same expression as its left-hand side -- a self-assignment on a struct member of a plain global variable. No conditional statement or unbraced control-flow body appears anywhere in the reproducer, so this is not a variable-declaration-scoping defect. To decide whether that assignment's target variable is provably dead, the optimizer consults a per-variable usage-summary helper that, before doing anything else, unconditionally reads a cached flag off the variable's own symbol-table bookkeeping record, recording whether that variable was ever given an initializer expression. That flag is implemented as a raw, non-owning pointer into the compiler's pool-allocated intermediate-representation arena, pointing at whichever IR node happens to actually own the initializer subtree; it is populated once, when the variable is first declared, and is never invalidated afterward. Earlier in that same optimization run, over the same function or a sibling one sharing the arena, the optimizer's own dead-code sweep had already determined some other statement -- one that happened to be the sole owner of that particular initializer subtree -- was itself unreachable or unused, and folded it away, handing its storage back to the pool allocator, which poisons freed regions in the ASan build. Nothing updates or clears the variable's cached pointer when its owning node is recycled this way, so the pointer is left dangling into freed, poisoned pool memory. When the dead-assignment check later runs over the self-assignment statement and asks this same variable for its usage summary again, the unconditional read of that stale pointer lands squarely in the poisoned region, producing the use-after-poison. The root defect is a missing invalidation step inside the compiler's own optimizer: pool-based node recycling during dead-code elimination has no mechanism to null out or otherwise inform every other IR node's cached pointers into the node being freed, so a symbol-table bookkeeping entry that cached a pointer into IR it does not own can be left dangling by the optimizer's own later work within the same compile -- a cross-pass IR-lifetime bug in the optimizer's own bookkeeping, not a front-end parsing/scoping bug, and not confined to any single control-flow construct.
