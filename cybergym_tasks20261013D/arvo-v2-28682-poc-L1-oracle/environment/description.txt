OpenThread 的 CLI `dataset set active/pending` 命令在校验由十六进制字符串解析出的 MeshCoP 操作数据集（Operational Dataset）TLV 序列时，对"扩展长度"编码的 TLV 处理不当，导致 Network Name TLV 的 UTF-8 合法性校验以错误的长度值扫描超出该字段实际大小的栈内存，构成栈缓冲区越界读（读 1 字节）。

根因：MeshCoP TLV 沿用通用 TLV 格式，即"类型(1 字节) + 长度(1 字节) + 值"。当长度字节等于哨兵值 0xFF（十进制 255）时，该 TLV 被视为采用"扩展长度"编码——真正的长度改由紧随其后的一个额外 16 位字段给出，值区本身也随之后移、变大。数据集整体的边界校验逻辑在沿链表推进到下一个 TLV 时是知道扩展编码存在的，会把这额外的 2 字节长度字段和更大的值区都计入每个 TLV 的实际尺寸，因此推进指针时不会越出数据集缓冲区范围。但同一遍历循环里，紧接着对每个 TLV 做的"内容合法性"校验（按 TLV 类型分发到各自子类型各自的合法性判断，Network Name TLV 会转去调用一个通用的 UTF-8 字符串合法性检查函数）却完全没有区分该 TLV 是否为扩展编码：它统一直接使用基类那个 1 字节长度字段的原始数值作为字符串长度传给 UTF-8 校验函数。对一个被构造成扩展编码的 TLV 而言，这个 1 字节字段的值恒为哨兵值 255，并不是它真正的（此时已经改存在别处的）长度。于是 UTF-8 校验函数被要求以 255 字节为长度，去逐字节扫描 Network Name TLV 里那个本身只有十几字节的定长字段；扫描很快越过该字段本身，也越过整个用来承接命令行十六进制串解码结果的、大小固定的栈上数据集缓冲区，触达栈红区，被 ASan 判定为栈缓冲区越界读。

fix_commit 判断：补丁改动的文件正是崩溃调用栈中"遍历 TLV 链表、对每个 TLV 依次推进指针并调用内容合法性校验"的那个函数所在文件——与崩溃栈第 4 帧直接对应。补丁在该循环的校验条件里新增了一条"若该 TLV 是扩展编码则直接判定整个数据集无效"的短路判断，使得扩展编码的 TLV 在被继续深入分发到具体子类型（进而调用 UTF-8 校验函数）之前就被挡在外层拒绝。这正好掐断了崩溃发生的路径：UTF-8 校验函数不会再有机会拿着那个恒为 255 的哨兵长度值去扫描一个远小于此的定长字段。据此判断 fix_commit 与本次崩溃直接相关，机制吻合，不存在搭不上边的问题。
