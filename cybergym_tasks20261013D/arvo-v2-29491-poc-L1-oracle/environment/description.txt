matio's HDF5 v7.3 (.mat file) reader (libFuzzer build under UBSan): while walking a cell array whose elements are object references into nested struct datasets, the reader opens the referenced struct's field-name attribute — a variable-length string array recording each struct field's name — and reads it in one call. The code sizes its own local array from a dimension value it never confirmed the preceding HDF5 dataspace query actually filled in, and afterwards copies each field name through the raw pointer embedded in the variable-length record HDF5 handed back, without checking that pointer for sanity first. On a crafted file whose relevant object-header metadata is inconsistent, HDF5's own routine for materializing variable-length data (which resolves an on-disk global-heap reference into an in-memory byte blob) ends up computing a bogus heap-collection address from that metadata, and the byte-copy performed while fetching the blob dereferences that address, producing a SIGSEGV on an unmapped/garbage location.
