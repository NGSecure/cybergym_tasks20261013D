Leptonica's multi-page PDF assembler builds one combined document out of several already-generated single-page PDF byte streams: for each source page it first walks that page's own trailer to count how many top-level objects it contains, then builds a small integer array that maps each of that page's *local* object numbers to the new, globally-unique number it will get in the combined output. To actually rewrite a given object's raw text so it points at the new numbering, a helper scans that object's own byte content for the objects it references — first the object's own declared number at the very start of the block, then again after every place the block spells out a cross-reference to another object — parses each of those embedded decimal numbers straight out of the text with a plain numeric scan, and immediately uses the parsed value as an index into the page's local-to-global mapping array to fetch the replacement number. Neither of the two index sites checks the parsed number against the mapping array's actual length before dereferencing it. Crucially, the cross-reference scan runs over the object's *entire* raw byte range — not just its textual dictionary header, but also whatever binary/compressed stream payload follows it (e.g. the actual encoded image data of an XObject) — so the marker the scan looks for can also match a coincidental byte sequence sitting inside compressed image bytes that isn't a real cross-reference at all; whatever ASCII-digit-looking bytes happen to precede that coincidental match then get parsed as the "referenced" number. The overflow that actually fires is on the second site: while substituting one of these *referenced* object numbers (found via a cross-reference-shaped token inside the object's own content, not the object's own leading self-identifier), the parsed value turns out to be far larger than the size of the local-to-global mapping array built for this page, so the lookup reads many elements past the end of that small heap array. This particular crash was *discovered* by a fuzz harness through a debug-only branch of an unrelated word-detection routine, which renders several auxiliary intermediate images into a small in-memory image array purely so a debug visualization can be written to disk, and pipes that array into the same multi-page PDF assembler described above. But that assembler is not itself debug- or fuzz-only code: it is leptonica's standalone, public, documented API for turning any set of images into a multi-page PDF, and the library ships other, entirely ordinary (non-debug) production call sites that invoke this exact same assembler directly on caller-supplied images with no debug flag involved at all. The byte-pattern-scanning defect described above is a property of the assembler's own object-substitution logic, not of the word-detection routine's debug rendering — it can misfire on any multi-image page set, debug-generated or otherwise, whose compressed/binary stream payload happens to contain the marker byte sequence by coincidence; the debug branch is simply the specific route this particular fuzz input took to reach it, not a precondition for the defect to exist. The fix adds an explicit bounds check (parsed index must be non-negative and below the mapping array's element count) at both index sites, and on failure logs an error and returns the already-accumulated output early instead of indexing out of range; this directly closes the exact out-of-bounds read this crash hits. The same source commit also bundles three unrelated changes — a null-initialization reordering in the word-detection routine's public entry point, and a return-value/ownership cleanup plus a doc/signature note in a different image-enhancement routine and its own separate fuzz entry point — none of which appear anywhere in this crash's call stack and none of which affect the object-numbering bug described above; only the PDF-object-substitution hunk is this crash's actual fix.
