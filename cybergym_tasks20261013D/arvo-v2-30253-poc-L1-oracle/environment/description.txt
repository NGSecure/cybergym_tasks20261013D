c-blosc2's in-memory frame decoder (reached when a super-chunk is opened directly from a raw serialized-frame buffer, e.g. via the decompress-frame fuzz target) suffers a wild-pointer memcpy while walking the frame's metadata-layer index: after locating a metalayer's content marker, the routine reads that metalayer's content length straight out of the header bytes as a signed 32-bit integer and uses it, unmodified and unvalidated, both as the size argument to `malloc` and as the byte count for the `memcpy` that follows. A crafted metadata-layer entry can set this length field to a negative value; the same negative value also defeats the preceding running-position bounds check, since adding a negative number to the cumulative position counter moves it backward instead of forward, so the check meant to catch a value that would walk past the frame's declared total length is trivially satisfied. Cast to `size_t` for the allocation call, the negative length sign-extends into an enormous, unsatisfiable size, so the allocation fails and returns NULL — but the return value is never checked, so parsing continues with a NULL destination pointer, and the subsequent `memcpy` is then invoked with that same huge length, using the NULL pointer as its destination while copying from just past the metadata index inside the (much smaller) header buffer that was actually allocated.
