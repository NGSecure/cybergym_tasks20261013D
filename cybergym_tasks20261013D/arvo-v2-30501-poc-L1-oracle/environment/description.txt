SerenityOS (UBSAN build), JavaScript-interpreter fuzz target: running a script that invokes the interpreter's built-in garbage-collection-trigger function as a tagged template call with no substitution values causes the interpreter's own diagnostic trace, emitted as part of that GC pass, to go through the argument-less overload of a shared debug-print helper -- the same helper implicated in three catalogued image-loader crashes in this codebase (a PGM sample-stream reader, a JPEG scan-header parser, and a BMP DIB-header/color-table decoder).

Root cause: the same shared-library defect as those siblings -- the debug-print helper's zero-argument overload builds an internal, zero-sized holder for the call's (nonexistent) type-erased arguments and then performs a member-function call through it, which the compiler's object-size check flags as operating on storage too small for a valid object of that type.

This finding is independent of the image-loader siblings: the interpreter's garbage-collection trigger shares no code path with any image-decoding routine, is exercised by its own fuzz target and its own PoC (a single argument-less GC-trigger call), and was tracked upstream as its own, separately timed issue. It is also independent of a second interpreter-side finding in this batch reached via a different operation (a failed property assignment's error-message formatting, rather than a GC trace) -- the two exercise unrelated interpreter code paths and different PoC scripts despite sharing the same fuzz target.
