One-sentence summary: Parsing a crafted Microsoft Access (.mdb) database file makes mdbtools' catalog/row-reading path suffer a 4-byte heap-buffer-overflow READ while walking a table's page-usage bitmap, because the bitmap buffer duplicated out of the table's on-disk definition can be far smaller than the fixed-size header the walking routine unconditionally assumes is present at its front.

Root-cause mechanism: When mdbtools opens a table's catalog entry, it locates and copies out the table's "page usage map" -- a small on-disk byte blob indicating which physical pages currently belong to the table -- into a freshly allocated heap buffer sized to exactly whatever length the on-disk row-length field for that blob says it is. That length comes straight from the file's own page/row layout, is not sanity-checked against any minimum, and can be as small as a single byte for a malformed table definition. The copied buffer is later handed unchanged to the page-scanning helper invoked while fetching rows (reached through the row/catalog data-fetch call chain as it walks table pages looking for the next data page): that helper assumes the buffer always begins with a fixed 5-byte header -- a one-byte map-type flag followed by a four-byte starting-page-number field -- and unconditionally decodes the four-byte field starting one byte into the buffer, with everything past offset 5 treated as a bitmap whose bit-length is computed by subtracting 5 from the buffer's total size. Nothing checks that the buffer is actually at least 5 bytes long before this decode happens. When the on-disk map blob is tiny (in the observed crash, exactly 1 byte), the heap allocation backing it is a matching 1-byte block, so the four-byte integer read starting at offset 1 runs past the end of that allocation. Because the size-minus-5 subtraction that derives the trailing bitmap's bit-length is done in unsigned arithmetic, an undersized buffer additionally makes that "remaining bits" count wrap around to a huge value, so a real run of this code would keep scanning far past the buffer even after the initial out-of-bounds read. This path is reached purely by opening the file and reading rows out of its system catalog -- no interactive input or unusual build options are needed, just a database file whose table-definition page declares an implausibly short usage-map length for one of its tables.

fix_commit assessment: fix_commit is directly on point. The patch adds an explicit minimum-size guard at the very top of the page-usage-map-walking helper described above, before it derives the starting page number or the bitmap's bit-length from the buffer -- rejecting (returning "nothing found" instead of decoding) any map buffer shorter than the 5 bytes its header-plus-bitmap layout requires. That is exactly the missing check whose absence lets a too-small map buffer (as small as the observed 1-byte allocation) reach the unconditional 4-byte decode that AddressSanitizer caught. The patched function is precisely the one that sits in the crash's own call stack immediately above the low-level integer-read primitive that faulted, and precisely the one that received the too-small buffer built earlier in the read path, so there is no ambiguity about this commit targeting the right code path.
