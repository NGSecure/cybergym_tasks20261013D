一句话：matio 在通过 HDF5 API 读取 MATLAB v7.3（即 HDF5 容器）文件时，为了判断某个数据集/引用对象上是否存在某个 MATLAB 专用属性，会调用 HDF5 的属性存在性检查接口；该接口内部需要顺序解码该对象头上挂着的每一个属性消息（含其内嵌的数据空间/维度描述子）才能跳到下一个消息或比对属性名，而 HDF5 自身这段数据空间描述子解码逻辑只信任消息里编码的维度/长度字段来决定要读多少字节，并不核对对象头缓冲区实际分配了多大空间。

崩溃机制（对照 error.txt 全文重新推导）：
- ASan 报告为 heap-buffer-overflow READ of size 1，SCARINESS 为 "1-byte-read-heap-buffer-overflow-far-from-bounds"（22 分），越界地址落在一个约 424 字节的堆块结束处再往后约 416 字节的位置——不是常见的"多读一两个字节"式差一错误，而是解码逻辑按某个被污染的计数/长度字段一路推进出去，落到离原缓冲区很远处才越界，说明触发条件是某个尺寸类字段被放大而非简单的下标漂移。
- 崩溃栈自顶向下依次是：HDF5 的数据空间消息解码函数 → 该消息所属的"共享消息"解码封装 → 某条属性消息本身的解码 → 该属性的共享消息解码封装 → 对象头消息迭代器 → 检查对象上是否存在某个具名属性的内部实现 → matio 侧对某个 HDF5 数据集对象调用的属性存在性探测接口（`Mat_H5ReadVarInfo` 在读取完 class 信息后，接着确认该变量是否被标记为全局变量时发起的调用）。matio 这一层只是想问"这个对象上有没有一个特定名字的属性"，并不关心也没有读取该属性的值，但 HDF5 为了回答"有没有"，必须把该对象头上已经存在的每一条属性消息（含排在目标属性之前的其它属性）逐一解码以确定各消息的边界，越界正是发生在解码某一条排在前面的、与本次要查询的属性名毫不相干的属性所附带的数据空间描述子时。
- 因此根因落在一份精心构造的 MAT v7.3/HDF5 文件本身：文件中某个对象头里存在一条属性消息，其内嵌的数据空间描述子编码了一个与该消息实际占用字节数不匹配（被放大）的维度/尺寸信息，HDF5 解码器据此推算出的读取长度或偏移量超出了该消息乃至整个对象头所在堆分配的真实边界。这属于 HDF5 库自身在解析畸形对象头时缺少边界校验的问题，matio 只是在做一次普通的"这个对象有没有某属性"的探测时，无意中把它触发了出来；探测的具体属性名（本例中是全局变量标记）与越界位置所在的那条属性彼此独立，谁排在对象头前面、谁携带了畸形数据空间描述子，才是决定是否触发的关键。

关于 fix_commit 的判断——**这个 fix_commit 可能有问题**：
crash.json 记录的 fix_commit 实际改动只有 4 行，且全部位于 matio 中处理"结构体分组信息"的另一个函数里：给该函数新增了一个前置判断，只有当对象被识别为结构体（MAT_C_STRUCT）类型时，才去检查它是否带有字段名列表属性。这个函数与本次崩溃所在的调用链（matio 读取单个变量/引用对象的基本信息、随后确认其是否为全局变量）是完全不同的两个函数，该改动本身也没有涉及任何属性存在性检查、消息迭代或数据空间/边界校验相关的代码，语义上和越界读没有直接关联。
