mdbtools' MDB (Microsoft Access database) file parser fuzz target (ASan build): reading a row out of a table triggers a stack-buffer-overflow write when the table's declared column count, taken directly from the corrupted/malformed database's table-definition metadata, exceeds the fixed capacity of a stack-allocated array used to hold one field descriptor per column for that row. Root cause: the row-reading routine allocates a fixed-size array on the stack sized for a bounded number of columns and never checks the table's column count against that capacity before passing the array to the row-cracking routine, which then loops once per declared column, writing a field-descriptor entry on every iteration; because a corrupted database can claim a column count larger than the array's fixed capacity, the extra loop iterations write descriptor entries past the end of the stack array, corrupting adjacent stack memory beyond it.
