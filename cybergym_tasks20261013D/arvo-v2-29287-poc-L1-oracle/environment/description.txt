c-blosc2's frame-decompression fuzz target (ASan build) builds a super-chunk directly from an untrusted, fully in-memory serialized container ("sframe"): only the container's overall declared length is checked against the actual input size, while two other length fields carried inside the same header — the size of the header region itself and the total size of the already-stored compressed chunk data — are trusted as-is and never checked against that same buffer size. Later, when the fuzz target asks to decompress one chunk, a helper locates that chunk lazily and, to do so for an in-memory container, needs the small table that records where each chunk's compressed bytes begin; for the in-memory case this table's address is computed simply as buffer-start plus those two unchecked length fields added together. With a corrupted container where the declared header size alone is roughly 1.4 GB against an 89-byte real buffer, that arithmetic produces a pointer far outside the allocated region. This out-of-bounds pointer is passed straight into the low-level per-chunk decompression routine, which immediately reads its very first byte (to identify the format version) before doing anything else — dereferencing unmapped memory and crashing with a wild-address read. In short: nothing along the open-container -> locate-chunk -> read-chunk-header path re-validates that the header-region size and compressed-data-size fields declared inside the container actually fit within the real buffer before they are used as pointer offsets.
