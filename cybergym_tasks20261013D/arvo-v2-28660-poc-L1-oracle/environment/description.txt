RDKit's molecule-pickle deserialization fuzz target unpickles a serialized molecule and then runs post-parse stereochemistry perception on it, which includes an iterative Cahn-Ingold-Prelog-style canonical-rank refinement over the atoms: each outer pass appends one new numeric invariant value onto a per-atom growable list and then recomputes, from the accumulated values of every atom, how many distinct rank classes currently exist. Once that distinct-rank count stops changing from one pass to the next (the classes have converged), the appending step effectively stops mattering, but the surrounding driver still unconditionally re-executes, on every single outer pass regardless of whether the rank count actually changed, a step that (a) writes the freshly computed rank value into a fixed slot of each atom's per-invariant list and (b) then truncates that list down to just that slot. The fixed slot is derived purely from the outer-loop iteration counter, with no check that the list has actually been grown enough times to contain that many elements.

Root cause: on a molecule (reconstructed from attacker-controlled pickle bytes) whose rank classes converge earlier than the loop's own iteration counter assumes, a given atom's per-invariant list is already the same length it was left at (or shorter than) after a prior truncation, but the loop keeps incrementing its iteration counter and keeps performing the fixed-slot write anyway. The write index ends up one element beyond that atom's already-truncated backing vector, so the assignment writes past the end of the heap allocation for that vector -- a 4-byte out-of-bounds heap write (ASan-detected), not a read, and not a use-after-free. Because this happens deep inside stereochemistry assignment that automatically runs whenever a pickled molecule is deserialized, no explicit stereo/chirality API call is needed from the caller -- simply unpickling a crafted, malformed molecule blob is enough to trigger the overflow.
