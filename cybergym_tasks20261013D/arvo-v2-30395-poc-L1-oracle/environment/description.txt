htslib's CRAM block decompressor, while reconstructing an rANS-decoded byte stream, runs a run-length expansion pass that writes repeated bytes into a caller-preallocated output buffer sized to the expected uncompressed length. Root cause: for a byte flagged as run-length-coded, the routine reads a run-length value from an accompanying side stream and expands it into `run_length + 1` repeated output bytes (the +1 accounts for the byte already implied by encountering the symbol itself), but the bounds check that precedes the write only confirms that writing `run_length` bytes — one fewer than what actually gets written — stays inside the output buffer. When a run lands so that exactly `run_length` bytes of space remain before the end of the buffer, the check is satisfied even though the real write is one byte longer, so the routine overruns the heap buffer by (at least) one byte. Because the run length is derived from the compressed CRAM block data supplied by the input file, a crafted file can size and position a run to land exactly on this off-by-one boundary and trigger the overflow deterministically.
