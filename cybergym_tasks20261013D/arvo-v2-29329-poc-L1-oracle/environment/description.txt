mdbtools 的 UBSan 构建在解析 Access 数据库目录表时,触发了一次数组下标越界:一个整数运算溢出出来的巨大负偏移,被直接当成页缓冲区里的下标使用,读到了这个固定大小页缓冲区之外的内存。

根因:表定义页里"真实索引数量"这个字段,在解析表结构的例程里被当作有符号 32 位整数直接从原始页字节中取出,不做任何取值范围校验。紧接着的"读取列元数据"步骤,用这个数量字段乘以每条索引项固定大小、再加上列区起始偏移,算出列数据应该从页内哪个位置开始读——这段乘加运算全部在 int 上进行,一旦这个数量字段是攻击者可控的异常值,乘积可以整体溢出成一个巨大的负数。带着这个已经为负的起始位置第一次调用底层的"按需翻页并拷贝若干字节到调用者缓冲区"的辅助例程时:例程开头判断"当前位置是否已经超出本页、需要翻下一页"的循环条件,对负值天然不成立,被直接跳过;紧接着判断"当前位置加上要拷贝的字节数,是否达到本页末尾"的循环条件时,当前位置(有符号、为负)按 C 语言的隐式类型转换规则被转换成无符号数再与要拷贝的字节数相加,回绕成一个极大的无符号值,使这个条件仍然成立、循环体照常执行——于是代码就用这个原始负值去对页缓冲区做指针运算,并把从那里开始的内存**读出**、拷贝进调用方提供的目标缓冲区。这块页缓冲区在句柄结构体里是一个固定 4096 字节大小的数组,UBSan 正是在这次数组下标运算上直接命中 "index -117374677 out of bounds for type 'unsigned char [4096]'"。这个翻页/拷贝辅助例程全程没有对起始位置是否为负做任何检查,是整条链路上唯一缺失的防线;这是一次越界**读**(越界的一端是页缓冲区本身,不是拷贝的目标缓冲区),不是越界写。

fix_commit c31daeb2 是否搭边:直接相关。补丁在这个翻页/拷贝辅助例程函数体最开头新增了一个"起始位置若为负则立即返回失败"的检查,正是本崩溃缺失的那道防线——一旦发现起始位置已经为负,就不再往下走翻页/拷贝逻辑,从根上堵死了这次页缓冲区越界读。补丁同时把此前所有忽略这个辅助例程失败返回值的上层调用点(读取列元数据、读取索引、读取目录、绑定列等多处),都改成检查失败并向上传播(释放已分配资源、返回失败、上层报错退出),这是配套的错误传播修正,服务于同一个"这个辅助例程现在可能失败"的新语义,不是与本崩溃无关的改动。改动分布在处理表结构、索引、数据行、目录以及 ODBC/SQL 上层接口的多个源文件里,全部是产品代码而非 fuzz harness 专用代码,不是"harness-only fix"。
