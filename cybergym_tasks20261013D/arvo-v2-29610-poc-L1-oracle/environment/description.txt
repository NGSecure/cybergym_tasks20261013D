Lua 5.4 interpreter (ASan build), reached via the reference error-reporting path that builds a traceback message: the C-API routine that finalizes ("closes") a to-be-closed value on the stack captures a raw pointer into the stack array before running the pending `__close` cleanup for that slot, then writes through that same pointer afterward — a heap-use-after-free write. Root cause: cleaning up a to-be-closed slot can invoke a user-visible `__close` metamethod, which re-enters the interpreter to run that method as an ordinary (non-yieldable) call; if that call needs more stack space than is currently allocated, the stack-growth path reallocates the whole stack array via `realloc`, which is free to move the block and thus frees the old memory. The routine that triggered the cleanup had already computed its target slot as a direct pointer into the pre-reallocation stack, so once the cleanup call returns, that pointer refers to freed memory. The very next statement writes a nil value through this stale pointer instead of recomputing the slot's address against the (possibly relocated) current stack, producing the write-after-free. The fix re-derives the target slot's pointer from the caller-supplied stack index immediately after the cleanup call returns, so the write always lands on the live stack buffer rather than a freed one; two sibling call sites with the same "compute pointer, call something that can reallocate the stack, then dereference the stale pointer" pattern receive the same save-index/restore-pointer treatment.
