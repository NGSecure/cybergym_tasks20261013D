mdbtools 在按行读取一张表时，会依次对每一列做"取值并写入调用方绑定的输出缓冲区"处理；其中某一类字段（存放长文本/备注内容的字段）需要先把数据库文件里按宽字符（UCS-2LE）编码存储的原始字节，转换成便于对外展示的字符集，再写进一块为这次转换临时分配、固定大小的目标缓冲区。这个转换过程用一个循环反复调用底层转换例程：每次调用后，如果遇到一个无法识别/无法转换的宽字符，代码会手动把这个字符替换成占位符写进目标缓冲区，并把"目标缓冲区剩余可写字节数"这个计数减一，然后继续下一轮循环——但循环本身并不检查这个剩余字节数是否已经耗尽就直接进入下一轮。根因不是"少判断了一次缓冲区满没满"这种普通遗漏，而是两个条件恰好叠加时的一个特定错误：当剩余字节数恰好因为上面这种"替换成占位符"的操作而减到 0，且紧接着下一个宽字符又恰好是同一种无法识别的情况时，底层转换例程即便被告知"没有剩余空间了"，也不会像空间不足时通常会做的那样立刻停手，而是照常返回"这个字符无法识别"；于是代码继续走同一条"替换成占位符再把计数减一"的路径——这一次是在剩余字节数已经是 0 的情况下再写入一个字节（越界写出目标缓冲区之外），并把这个已经是 0 的计数再减一。由于这个计数是无符号类型，减一的结果不是变成 -1，而是直接下溢成一个极大的数值。此后循环继续调用底层转换例程时，会把这个极大数值当作"缓冲区还非常宽裕"，从而对后续本该正常处理的宽字符持续写入，写入位置早已越过目标缓冲区边界——越界的范围从一次多写一个字节，直接放大成一段不受限、可以覆盖到该缓冲区之后任意范围堆内存的连续越界写。

这也解释了为什么这次崩溃的调用栈停在的位置，和真正发生越界写入的那段代码完全对不上：本次 PoC 里，被这段连续越界写破坏的堆内存，覆盖到了后面某一个字段在"绑定"阶段用来记录"这个字段的值应该写到哪个地址"的指针本身。等按列顺序处理到那一列、发现它的值长度为零、只需要往它自己的绑定地址写一个空字符串时，程序实际使用的却是已经被前面的越界写篡改过、变成一个随机高位地址的指针，于是在一次看似平平无奇的"写空字符串"操作上触发了野指针崩溃——这条崩溃路径本身的字段处理逻辑没有任何问题，它只是这次堆内存损坏之后第一个不巧被撞上的受害者。
