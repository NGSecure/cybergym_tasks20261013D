SerenityOS (UBSAN build), BMP image-loader fuzz target: decoding a malformed Windows BMP file whose DIB (device-independent bitmap) header advertises a bit-depth/compression combination that requires a color table causes the loader's DIB-header decoding step -- invoked while the loader is building that color table, ahead of decoding the actual pixel data -- to hit a header field value it flags as invalid, and it reports that condition through the same argument-less string overload of the shared debug-print helper implicated in two sibling image-loader crashes in this codebase (a PGM sample-stream reader and a JPEG scan-header parser, respectively).

Root cause: the same shared library defect as those two siblings -- the debug-print helper's zero-argument overload builds an internal, zero-sized holder for the call's (nonexistent) type-erased arguments and then performs a member-function call through it, which the compiler's object-size check flags as operating on storage too small for a valid object of that type.

This finding is independent of both siblings: BMP's DIB-header/color-table/pixel-data decoding chain shares no code path with either the PGM sample reader or the JPEG scan-header parser, is exercised by its own fuzz target and its own malformed-BMP proof-of-concept file, and was tracked upstream as a third, separately timed issue. In this particular build the compiler's inlining appears to have folded the debug-print call fully into its immediately enclosing BMP function rather than leaving it as a separately attributed frame, which is likely why this report's crash-site attribution takes a different shape from its two siblings even though the underlying defect and source location are the same.
