c-blosc2 decompress-frame fuzz target (ASan build): a wild-pointer SEGV occurs while locating the compressed-offsets lookup table that maps a chunk index to its byte position inside a super-chunk frame. Root cause: to find where that table sits in the in-memory frame buffer, the code adds two 64-bit fields it reads directly, unvalidated, from the crafted frame's fixed-size header (a parsed header length and a compressed-bytes count) and compares the sum plus a small fixed extra against the frame's declared total length to reject a table location that would run past the buffer's end. That comparison assumes the addition cannot misbehave, but it never guards against the addition itself overflowing signed 64-bit arithmetic: a large-enough crafted compressed-bytes value makes the sum wrap around to a small or negative number, which then sails straight through the "greater than total length" bounds test even though the true, non-wrapped position is nowhere near valid. The resulting table pointer can end up pointing arbitrarily far outside the allocated frame. Immediately afterward, a low-level routine that parses a fixed-size record header is invoked on that pointer, but it is called with a hard-coded "assume the caller's buffer is huge" size argument instead of anything derived from the real, much smaller allocation, so it unconditionally copies a fixed number of bytes from wherever the wrapped-around pointer lands — dereferencing unmapped/poisoned memory and crashing with SIGSEGV before any further validation can run.
