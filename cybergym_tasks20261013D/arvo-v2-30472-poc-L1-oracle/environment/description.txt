wolfSSH server-side SSH user-authentication handling (ASan build): when a client authenticates with an ECDSA public key, the server extracts a length field from the client-supplied key blob (the byte length of an embedded public-key-type identifier string) and, on an apparent mismatch against the length recorded earlier in the handshake, immediately uses that length as the byte count for a raw memory comparison against the earlier string — without first checking that the value is sane or that it does not exceed how many bytes are actually present in the received packet. Root cause: the length is decoded through a wire-parsing helper that only verifies the 4-byte length field itself fits inside the buffer, never that the value it produces is bounded by the bytes remaining in the packet, so a client can supply an arbitrarily large length. The subsequent raw-memory-comparison call is then made with that huge, attacker-chosen size; AddressSanitizer's interceptor rejects the call outright because the requested comparison size is enormous (effectively invalid when treated as a bounded count) before any out-of-bounds byte is actually touched.
